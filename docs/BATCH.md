# 计薪批次：在途班次的规则裁决与可重放

## 裁决

规则版本绑定的是**整班**，不是单个分钟片段，也不是每条打卡。

| 班次形态 | 绑定版本 | 计入期间 |
|---|---|---|
| 归属日与完成时点同处一个版本区间 | 该版本 | 归属日所在期间 |
| 归属日在前一版本区间，完成时点（OUT）已跨过切换点 | 完成时点所在版本 | 完成时点所在期间 |

在途班次（10-31 22:00 进、11-01 06:00 出）因此整班按 11 月版本计价，只在新期间生成一次应付；
原期间批次只登记「本期不重复计薪（已转出）」依据，不生成应付。

为什么不选另外两种做法：

- 整班沿用旧规则：切换后实际发生的工时会整体逃逸新规则。
- 按时点切成两段：同一班次同时引用两套规则，无法作为一次结算重放，旧账也难复核。

约束由此得到保证：每个片段只落在一个规则版本、一个期间、一个批次，且只有一个切换依据。

## 批次内容

每个计薪批次（`app/payroll/batch.py`）保存并导出四层一一对应的记录：

| 层 | 内容 | 对应关系 |
|---|---|---|
| 切换依据 | 归属日、工作起止、切换点、绑定版本、计入期间、判定与理由 | `basis_id` |
| 原始班次 | 选中与来源打卡行（含来源行号、原始字段） | `shift_id` |
| 工时片段 | 日历日、起止、分钟、时薪、规则版本 | `segment_ref` |
| 应付 | 分钟、倍率、分类、金额、规则版本 | `payable_id` |

`应付.segment_ref → 片段.segment_ref`，`片段.basis_id → 依据.basis_id → 原始班次.shift_id`。
对账函数独立重算：片段是否都被计薪、分钟是否守恒、单片段是否只有一个版本、应付合计是否等于批次总额。
批次一旦不平（`reconcile.balanced=false`）状态即「应付未对平·不可封存」，`POST /api/batches/<key>/seal` 返回 422。

## 身份、重跑与失效

- `batch_key = sha256(期间, 本批证据摘要, 规则注册表摘要)`。
- 同源重跑得到同一个 key：复用同一批次，不会二次计薪（`runs` 幂等 + `batches` 唯一键）。
- 补卡或规则更新改变证据或规则摘要：生成新一代批次，同期间旧批次标记 `已作废` 并写 `superseded_by`，
  记录保存在 `batch_events`；旧批次的原始班次、切换依据、应付全部保留且可重放。
- 期间应付合计只统计非作废世代（`GET /api/periods/<period>/totals`）。

## 规则切换失败

`parameters.rule_switch` 非法（时区缺失、非 1 日 00:00、倍率非正、版本重复、时点回溯）时：
切换状态记为「失败」，规则注册表保持旧版，批次身份不变，已有批次不受影响；失败原因进入运行证据与页面提示。
以 `replace: true` 可修正同一生效时点的版本，这会更换规则摘要，从而生成新批次并作废旧批次。

## 重放

`GET /api/batches/<key>/replay` 仅使用批次自带的规则注册表与原始班次记录重建全部应付，逐项比对
分钟、倍率、分类、金额、规则版本与依据 ID，并核对合计。页面顶部「重放」显示逐项一致或差异数。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/batches?period=YYYY-MM` | 列出批次世代 |
| GET | `/api/batches/<key>` | 批次详情与事件流水 |
| GET | `/api/batches/<key>/replay` | 重放校验 |
| GET | `/api/batches/<key>/export.csv` | 导出本批证据（CSV） |
| POST | `/api/batches/<key>/seal` | 对平后封存；不平 422、作废 409 |
| GET | `/api/periods/<period>/totals` | 期间有效应付合计 |

页面在 `/m8_batch`。
